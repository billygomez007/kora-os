# Kora OS Data Model

Status: Foundation baseline
Database: PostgreSQL

## 1. Modeling rules

- PostgreSQL is the authoritative source of truth.
- Primary keys are globally unique UUIDs generated by trusted application or database code.
- All timestamps use UTC `timestamptz`; business-local dates use the branch time zone.
- Money is stored as integer minor units with a three-character ISO currency code.
- Tenant-owned tables include a non-null `organization_id`.
- Important tenant relationships use composite constraints where practical to prevent cross-organization references.
- Mutable catalog data may be archived; confirmed financial and audit history is never silently deleted.
- Human-readable references are separate from primary keys.
- Status values are explicit enums or constrained strings and are changed only through application state machines.
- JSON is reserved for flexible metadata, provider payloads, and audit snapshots, not normal relational data.

## 2. Identity and access

### `users`

Global human identity.

- `id`
- `email_normalized` nullable and unique when present
- `phone_e164` nullable and unique when present
- `display_name`
- `password_hash` nullable when an external identity provider is used
- `status`: pending, active, suspended, deleted
- `email_verified_at` nullable
- `phone_verified_at` nullable
- `created_at`, `updated_at`

At least one usable identity method is required before activation.

### `auth_identities`

Maps a user to an authentication provider.

- `id`, `user_id`
- `provider`
- `provider_subject`
- `created_at`, `last_used_at`

Unique: `(provider, provider_subject)`.

### `sessions`

Revocable device sessions.

- `id`, `user_id`, `device_id`
- `refresh_token_hash`
- `created_at`, `last_used_at`, `expires_at`, `revoked_at`
- `ip_hash` nullable, `user_agent` nullable

### `devices`

Registered application installations and push destinations.

- `id`, `user_id`
- `platform`: android, ios
- `installation_id`
- `push_token_ciphertext` nullable
- `app_version`, `last_seen_at`, `revoked_at`

Unique: `(platform, installation_id)`.

## 3. Organizations and branches

### `organizations`

- `id`
- `name`, `slug`
- `business_type`
- `default_currency`
- `time_zone`
- `country_code`
- `status`: onboarding, active, suspended, closed
- `created_by_user_id`
- `created_at`, `updated_at`, `archived_at`

### `branches`

- `id`, `organization_id`
- `name`, `code`
- `phone`, `email`
- `address_line`, `city`, `region`, `country_code`
- `time_zone`, `currency`
- `status`: active, inactive
- `created_at`, `updated_at`, `archived_at`

Unique: `(organization_id, code)`.

### `organization_memberships`

Connects a global user to an organization.

- `id`, `organization_id`, `user_id`
- `status`: invited, active, suspended, removed
- `joined_at`, `suspended_at`, `removed_at`
- `created_at`, `updated_at`

Unique: `(organization_id, user_id)`.

### `membership_branch_assignments`

- `organization_id`, `membership_id`, `branch_id`
- `created_at`

Unique: `(membership_id, branch_id)`.

### `roles`

- `id`, `organization_id` nullable for system templates
- `code`, `name`, `description`
- `is_system`, `created_at`, `updated_at`

### `permissions`

- `id`, `code`, `description`

Permission codes are stable, for example `transactions.record_payment`.

### `role_permissions`

- `role_id`, `permission_id`

Unique: `(role_id, permission_id)`.

### `membership_roles`

- `organization_id`, `membership_id`, `role_id`
- `created_at`

One membership can hold multiple roles.

- `payload_ciphertext` or protected payload reference

### `usage_counters`

- `id`, `organization_id`, `entitlement_code`

## 11. Required indexes

Every foreign key is indexed where join direction requires it. Additional high-value indexes include:

- Membership by `(organization_id, user_id, status)`.
- Branch assignments by `(organization_id, membership_id)`.
- Customers by organization plus normalized phone, email, and searchable name.
- Appointments by `(organization_id, branch_id, starts_at, status)`.
- Appointment provider and time range for conflict checks.
- Queue by `(organization_id, branch_id, status, position)`.
- Service sessions by branch, provider, status, and start time.
- Transactions by `(organization_id, branch_id, created_at)` and status.
- Payments and verifications by transaction and status.
- Commission records by staff and finalized date.
- Subscription by organization and current status.
- Audit events by organization, entity, actor, and occurred time.
- Outbox events by processing status and next attempt time.

## 12. Critical constraints

- All line totals and transaction totals are non-negative except explicit adjustment or reversal types.
- Currency codes on a transaction and its normal line items and payments must agree unless currency conversion is deliberately introduced later.
- Appointment and service-session end times must be after start times.
- Payment verification references the responsible provider and the same tenant as its payment and transaction.
- Commission records cannot become finalized before a confirmed verification outcome.
- Subscription trial and billing period end times must be after their corresponding start times.
- Cross-tenant relationships are rejected by database constraints where feasible and always rejected by application policy.

## 13. Transaction boundaries

One database transaction is required for:

- Organization creation, owner membership, first branch, trial subscription, and baseline role assignment.
- Payment recording, idempotency record, transaction transition, audit event, and outbox event.
- Provider confirmation, verification transition, transaction confirmation, commission creation, audit event, and outbox event.
- Dispute resolution and resulting financial state changes.
- Refund completion, reversal records, commission reversal, audit event, and outbox event.

## 14. Data lifecycle

- Catalog and staff records are archived rather than deleted when referenced by history.
- Session and idempotency records have controlled expiration.
- Provider webhook payloads have a limited retention policy and protected access.
- Financial, receipt, subscription, reconciliation, and audit retention policies are defined before production launch.
- Account deletion anonymizes eligible personal fields while preserving records that Kora is legally or operationally required to retain.

## 15. Migration rule

Every production schema change uses a reviewed forward migration. Destructive development fallback migrations are removed before real customer data is introduced. Seed data is isolated to development and test environments and is never embedded in production application behavior.
